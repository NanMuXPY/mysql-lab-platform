# 4核8G 容量实测报告

> 目的：把"一台 8G 能扛多少人"从推算值变成实测数字。
> 时间：2026-10-31 18:40–19:30　机器：阿里云 4 核 / 7526 MB（Ubuntu 24.04）

## 一句话结论

**4 核 8G 舒适承载 30 人（72.7s 全部就绪、30/30 登录成功）；硬上限 44 人，但到那个规模系统已经失去响应，不能当生产配置用。**

此前文档里"8G ≈ 55 实例"是纯内存除法推算，实测证明**真正的天花板不是内存，而是内核 AIO 事件上限**——不调这个参数，50 个实例只能成功 24 个。

## 测试环境

| 项 | 值 |
|---|---|
| CPU / 内存 | 4 核 / 7526 MB（无 swap，测试后补 2G） |
| 系统 | Ubuntu 24.04.5 LTS，Docker 29.1.3 |
| 镜像 | mysql:8.0（684 MB） |
| 金镜像 | data/gold/mysql-8.0，196 MiB / 149 文件 |
| 容器限额 | 0.5 核 CPU / 256 MB 内存 |
| 交付并发 | 5（另一轮对比 10） |
| 端口池 | 33001–33100 |

## 四轮结果

| # | 实例数 | 并发 | fs.aio-max-nr | 交付耗时 | 成功/失败 | 真实登录 | 容器内存合计 | 主机 available |
|---|---|---|---|---|---|---|---|---|
| 1 | 20 | 5 | 65536 | **49.3s** | 20 / 0 | 20/20 | 2788 MiB | 3869 MB |
| 2 | 30 | 5 | 65536 | **72.7s** | 30 / 0 | 30/30 | 4175 MiB | 2387 MB |
| 3 | 50 | 5 | 65536 | 209.5s | **24 / 26** | 24/24 | — | 3214 MB |
| 4 | 50 | 5 | **1048576** | 188.6s 时 44 个就绪 | **44 / 6** | — | — | **133 MB** |
| 5 | 30 | **10** | 1048576 | 69.9s | 30 / 0 | 30/30 | 4197 MiB | — |

- 单容器实际内存稳定在 **139 MiB**（限额 256 MiB，即限额只用了 54%）
- 首个实例 12–22s 就绪，尾个实例与总耗时基本重合（队列排满）

## 关键发现：内核 AIO 上限才是真天花板

**现象**：50 个实例只成功 24 个，26 个在创建阶段失败，日志里全是容器状态异常：

```
bootstrap exec 失败: 409 Conflict ("container xxx is not running")
bootstrap exec 失败: 409 Conflict ("Container xxx is restarting")
```

而**内存还剩 3.2 GB**，端口充足，磁盘充足——所有常规指标都正常。

**定位**：24 这个数字太整齐。查内核参数 `fs.aio-max-nr = 65536`，
MySQL 8.0 每个实例启动时通过 `io_setup()` 申请约 2700 个 AIO 事件：

```
65536 ÷ 2700 ≈ 24   ← 与实测成功数完全吻合
```

第 25 个 mysqld 申请 AIO 失败 → 进程退出 → 容器重启策略反复拉起 → 平台侧看到的就是 `is restarting`。

**修复**：

```bash
sysctl -w fs.aio-max-nr=1048576
echo "fs.aio-max-nr = 1048576" > /etc/sysctl.d/99-mysql-lab.conf
```

调大后 44 个成功（另外 6 个是内存见底后 Docker daemon 超时：`DockerException` / `ReadTimeout`）。

这个坑的危险之处在于**报错文本完全指向错误方向**：没有 "aio"、没有 "memory"，
只有容器"没在运行"。已经把它写进 `config.check_startup()`——启动时按端口池容量
反查 AIO 上限，不足就告警并直接给出修复命令。

## 容量结论

内存账（8G / 7526 MB）：

```
系统与 Docker 常驻        ~700 MB
单实例空载                 139 MiB
学生实际使用（buffer pool 涨上来）  160–180 MiB
留给系统的安全余量          ~1000 MB
────────────────────────────────────────
舒适区 = (7526 - 700 - 1000) / 160 ≈ 36 人
```

对照实测：

| 规模 | 状态 | 判断 |
|---|---|---|
| 20 人 | 49s，余 3.8 GB | 轻松 |
| **30 人** | **72.7s，余 2.4 GB，SSH/HTTP 正常** | **推荐** |
| 35–40 人 | 未实测，按曲线推算余量不足 1 GB | 临界，不建议 |
| 44 人 | 188.6s 才凑齐，available 仅 133 MB | **上限，系统已失去响应** |
| 50 人 | 6 个失败（Docker daemon 超时） | 不可用 |

**生产建议**

- 4 核 8G：**一个班 30 人**，2 小时实验课，成本约 ¥2/课时
- 40 人以上：8 核 16G，或两台 8G 按班级拆分（教师端可开两个实验单）
- 无论多大机器，**先调 `fs.aio-max-nr`**，否则 24 个封顶

## 并发度的取舍

`LAB_CREATE_CONCURRENCY` 从 5 提到 10，30 实例 72.7s → 69.9s，**只快 3.8%**。

说明瓶颈在 CPU（每个 mysqld 初始化都是 CPU 密集），不在调度并发度——提高并发只是把
同样的活排得更挤，还更容易触发超时。**保持默认 5 更稳**。

（`性能重审-2026-10-31.md` 里"换 8G 后上调并发到 10"这条建议，实测后判定为收益不足，撤回。）

## 复现步骤

```bash

# 2. 金镜像一次性生成

# 3. 分级压测（每轮自动回收，不残留实例）
./venv/bin/python scripts/stress_test.py --n 20
./venv/bin/python scripts/stress_test.py --n 30
./venv/bin/python scripts/stress_test.py --n 50
```
