## 二、项目简介条目（三个版本，按岗位挑一条用）

### A. 云运维 / 云计算岗（主推）

> **MySQL 实验环境一键交付平台** ｜ 独立设计与开发 ｜ Python · Docker · Linux
>
> **背景**：数据库实验课需为每名学生单独准备 MySQL 环境。原先靠人工逐台配置，课前准备 1–2 小时，版本不统一、误删库频发、课后环境无人清算；而按人购买云数据库（RDS）在 30 人规模下月费数千元，教学场景无法承受。
>
> **职责**：独立完成方案选型与全量实现——基于 Docker SDK 的容器生命周期编排、端口池租约与僵尸实例对账、金镜像预初始化、systemd 托管与开机自愈、内核参数调优与容量压测、鉴权与凭据加密（JWT 角色门禁 / PBKDF2 / Fernet）。
>
> **成果**：单台 4 核 8G 服务器实测 72.7 秒完成 30 人环境交付且 30/30 登录成功，单实例内存 139 MiB；建实例耗时由 85 s 优化至 15 s（金镜像预初始化，5.7×）；定位并修复内核 `fs.aio-max-nr` 造成的"第 25 个实例必崩"隐性天花板，使容量上限从 24 提升到实测 44；按课表启停后单课时成本约 ¥2，与按人采购云数据库相差两个数量级。

### B. 后端开发岗（Python）

> **MySQL 实验环境一键交付平台** ｜ 独立开发 ｜ FastAPI · Docker SDK · SQLite
>
> **背景**：面向高校数据库课的 SaaS 式实验环境交付系统，教师一键开课，学生获得隔离的独立 MySQL 实例，课后自动回收。
>
> **职责**：设计并实现 FastAPI 后端（25 个接口）、SQLite 元数据层（WAL + `BEGIN IMMEDIATE` + 进程内写锁，解决并发交付下的写冲突）、异步任务模型（接口立即返回、线程池限流 5 并发、前端轮询进度）、基于 sqlglot AST 的 SQL 错因诊断（语法错误 / 表不存在 / 列不存在 / 无 WHERE 的危险 UPDATE / JOIN 缺 ON），以及不建账号体系的学生自助端（凭 token 内学号取数，改 URL 也越权不到他人数据）。
>
> **成果**：30 实例并发交付 72.7 s 全绿；错题诊断可按学生回放其实际执行过的每一条命令，并输出「一人一行」的练习报告 CSV（未练习者也占位）；接口验收 25 项、生命周期 22 项、真浏览器 E2E 15 项全部通过；系统经两次完整重启与一次从零重装验证，元数据零丢失。

## 三、四个关键取舍（说明高概率追问）

**1. 为什么用容器，不用 RDS / 云主机？**
教学场景是可信用户、短时、可重置，容器够用；30 个 RDS 实例月费数千元，而一台 4 核 8G 就能扛一个班。同时**主动承认**：容器共用内核，不是安全边界。代码里把"创建实例"抽象成 provider 接口，将来换 KVM / 轻量云主机不动上层业务。

**2. 为什么不 Kubernetes？**
单机 30 个短生命周期实例，引入 K8s 只增加控制面开销和排障成本，收益为零。这是取舍不是不会。

**3. 为什么元数据用 SQLite 而不是 MySQL？**
元数据只有 5 张表、写操作集中在开课时几秒内，SQLite 零运维、随磁盘走、备份就是拷一个文件。用 WAL + `BEGIN IMMEDIATE` + 进程内写锁解决并发写冲突；在线备份必须走 `Connection.backup()`，直接 `cp` 会丢掉 WAL 里未合并的事务。

**4. 2 核 4G 的生产机为什么不用 docker-compose？**
实验容器是运行时由 SDK 动态创建的，compose 只能管 app 这一层；单进程宿主机部署 + systemd `Restart=always` 更轻，还把 200MB 内存省给学生的实例。

## 六、接手：让它跑起来

### 6.1 本机（Windows，只写代码）

```bash
python -m venv venv && venv/Scripts/pip install -r requirements.txt
venv/Scripts/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

**本机没有 Docker 也能起**教师端界面（只是建实例会失败）。首次启动自动建表、建 3 个种子账号、生成 `.env`。

### 6.2 生产机（2 核 4G / Anolis 3）

全套命令见 **`docs/部署说明.md` 第七节**，逐条可复制。四个不可跳过的前提：

1. `fs.aio-max-nr=1048576`（不设，第 25 个实例起必崩）
2. 2G swap + `vm.swappiness=10`
3. 依赖装进 `venv`，**不要装系统 site-packages**（cron 排障时吃过这个亏）
4. 公网 IP 用 systemd drop-in 覆盖，不改模板

### 6.3 更新代码后

```bash
# 生产机上
systemctl restart mysql-lab && sleep 3 && curl -s localhost:8000/healthz
python scripts/task9_test.py http://127.0.0.1:8000    # 25 项接口验收
```

### 6.4 接管密钥与账号

- SSH 私钥：`tools/mysql-lab-key-hy.pem`（唯一可用；用户名含中文会导致 ssh 找错默认密钥目录，必须显式 `-i`）
- 平台种子账号：首次启动随机生成并打印在日志里，`journalctl -u mysql-lab | grep -i 密码`
- **`data/.env` 的 `APP_SECRET` 是学生库密码的解密密钥**，必须与 `data/app.db` 一起备份，丢了密码就解不开

## 七、运维手册

### 7.1 日常命令

```bash
systemctl status mysql-lab        # 服务状态
journalctl -u mysql-lab -n 50     # 日志（同时落 /var/log/mysql-lab/app.log）
tail -20 /root/reconcile.log      # 对账记录（每小时）
free -m                           # 内存水位，Swap 应保持低占用
docker ps --format "{{.Names}}\t{{.Status}}"   # 学生实例
```

### 7.2 故障速查

| 症状 | 先查 | 处理 |
|---|---|---|
| 界面打不开 / 502 | `systemctl is-active mysql-lab` | 起服务；起不来先看 `journalctl` 有没有 `HMAC key must not be empty`（`.env` 缺 `APP_SECRET`，重启会自动补） |
| 实例全部消失但界面显示"运行中" | `docker ps -a` | 状态漂移，跑 `python scripts/reconcile.py` 拉起；若容器起不来见坑 2 |
| 容器 `Restarting (1)` | `docker logs <容器> 2>&1 \| tail` | 见第八节坑 2（`DAC_OVERRIDE`） |
| 第 25 个实例起批量失败 | `sysctl fs.aio-max-nr` | 见第八节坑 1 |
| 到期不自动回收 | `grep . /etc/cron.d/mysql-lab-reconcile`；`grep mysql-lab /var/log/cron` | 见第八节坑 3、4 |
| 学生连不上 | `ss -lntp \| grep 330`；云安全组 | 端口未监听 → 容器没起来；端口在但连不上 → 安全组没放通端口段 |
| 磁盘满 | `du -sh data/labs` | 先删 `recycled` 实验单的残留目录；容器日志已限 10m×2 |
| 内存告急 | `free -m`；`docker stats --no-stream` | 确认没有超量的活跃实验单；`reconcile.py` 会收掉到期实例 |

### 7.3 备份与恢复

```bash
# 在线一致性备份（必须用 backup()，直接 cp 会丢 WAL 里未合并的事务）
./venv/bin/python -c "
import sqlite3
src=sqlite3.connect('data/app.db'); dst=sqlite3.connect('/root/backup/app.db')
src.backup(dst); dst.close(); src.close()"
tar czf /root/backup/labs-$(date +%F).tgz -C data labs
cp data/.env /root/backup/env-$(date +%F)     # 与 app.db 必须配套
```

恢复：拷回 `data/app.db` + `data/labs/` + `data/.env` → `systemctl restart mysql-lab`。
**只恢复 db 不恢复 env，学生密码全部解不开。**

## 八、七个坑（都已修，但改代码时容易再犯）

这七条是本项目最值钱的部分：全部是"首次部署完全正常，只在重启或换机器时才暴露"的问题。

| # | 现象 | 根因 | 现状 |
|---|---|---|---|
| 1 | 第 25 个实例起容器反复重启，日志只有 `is not running`，内存端口磁盘全正常 | 内核 `fs.aio-max-nr=65536`，MySQL 8.0 每实例申请约 2700 个 AIO 事件，`65536/2700≈24` 就是假天花板；报错文本完全不指向这里 | `config.check_startup()` 启动时按端口池容量反查 AIO 上限，不足直接打印修复命令 |
| 2 | 容器 `Restarting (1)`，日志 `find: /var/lib/mysql/<db>: Permission denied` | `cap-drop ALL` 连 `DAC_OVERRIDE` 一起去掉，容器内 root 进不去属主 mysql、权限 750 的库目录。**首次启动库目录不存在，所以不报错** | `MYSQL_REQUIRED_CAPS` 补 `DAC_OVERRIDE` |
| 3 | 重启后全班实例静默停止，界面仍显示"运行中" | `restart_policy=on-failure`，而关机时 mysqld 收到 SIGTERM 正常退出（code 0），策略不触发 | 改 `unless-stopped`：机器重来自动拉起，教师手动 stop 仍不拉起 |
| 4 | 实验单到期不自动回收 | `/etc/cron.d` 里解释器写的是系统 `python3.11`，依赖却在 `venv` 里；换干净机器就 import 失败（本机因 site-packages 有历史残留包，差点漏判） | cron 模板改用 `/root/mysql-lab/venv/bin/python` |
| 5 | cron 文件放着但从未执行 | `/etc/cron.d` 格式要求「时间表达式 + 用户 + 命令」，漏字段会被 cron **静默丢弃**（不报错） | 已重写标准格式，并加每分钟探针验证真实触发 |
| 6 | 线上备份恢复后丢最后几笔事务 | SQLite WAL 模式下未 checkpoint 的写还在 `-wal` 文件里，`cp app.db` 拿不到 | 备份统一走 `Connection.backup()` |
| 7 | 脚本推到服务器后 cron 不认 / 报 `bad interpreter` | Windows  checkout 成 CRLF，shebang 带 `\r` | `.gitattributes` 强制 `*.sh`、`cron-*` 为 LF |

**验收口径的教训**：容器 `Up` 不代表可用（坑 2 就是 Up 之后立刻进重启循环）。重启验证必须进容器执行一条 SQL：

```bash
docker inspect <容器> --format "Restarts={{.RestartCount}}"    # 必须为 0
docker exec <容器> mysql -h127.0.0.1 -u<账号> -p<密码> -e "select 1"
```

## 十、边界与未做（诚实清单）

**已明确不做**：自动评分、题库管理、多机调度、学生自助注册、Web 版 SQL 客户端、K8s 化、HTTPS 前置。

**已知限制**：

- MySQL 的 1064 纯语法错误在解析阶段就被拒绝，**不写入 `general_log`**，客户端侧采集不到；平台通过 sqlglot 在服务端侧预解析同一条语句覆盖
- 容器共用内核，非强隔离；`cap-drop ALL` + 非 root + pids 限制只是收敛面
- 单机方案的天花板就是单机：40 人以上需 8 核 16G 或按班级拆两台
- HTTPS：方案已备好（模板 `deploy/nginx-mysql-lab.conf` + 部署说明第九节），**生产机尚未启用**；启用需要一个域名 + 约 15 分钟，流程照抄即可
- 学生 33001-33100 是 MySQL 明文协议直连（不经 HTTPS）；防线在库级账号授权 + 随机密码 + 容器收敛
- 元数据无版本化迁移，改表结构需手写兼容逻辑

## 十一、安全基线（v1.0.2 新增）

v1.0.1 的鉴权是"该挡的都挡了"，但**抗打击能力为零**：接口没有一处限制频率，
也没有一个中间件。挂公网后有三条真实缺口，v1.0.2 补齐，代码在 `app/security.py`。

### 11.1 三条缺口与做法

| 缺口 | 风险 | v1.0.2 做法 |
|---|---|---|
| 登录可无限试密码 | 教师账号能导出全班数据库密码，是最值得爆破的入口 | 连错 5 次锁 5 分钟，返回 429 + `Retry-After` |
| 无任何中间件 | 教师端带 JWT，被 iframe 嵌套即可点击劫持；响应体带全班凭据，被中间缓存即泄漏 | 统一加 CSP / `X-Frame-Options: DENY` / `nosniff` / `Referrer-Policy`，API 一律 `no-store` |
| 只有存活探针 | 学生说"很卡"时无任何定位依据 | 每个请求记 method / path / status / 耗时，≥1s 升 WARNING |

配套：**失败登录也写审计**（`login.failed` / `student.login.failed`）。
v1.0.1 只在成功时留痕，被撞库了事后查不出来；现在 `GET /api/audit` 能直接看到失败来源 IP。

### 11.2 三个设计取舍（说明可讲）

**① 限流状态放进程内存，不引 Redis。**
单进程 systemd 部署，多一个中间件就多一个故障点。代价是重启后计数清零——可接受，
因为重启是运维动作，攻击者触发不了。将来真要多副本，把 `FailLimiter` 换成 Redis 实现即可，
调用方（`main.py` 两处 `check/fail/reset`）不用改。

**② 限流的键是「IP + 账号」，不是只有 IP。**
机房出口 NAT 后整班共用一个公网 IP，只按 IP 限流 → 一个学生连错 5 次，全班一起被锁。
按账号 + IP 组合，既挡得住单账号爆破，又不误伤。账号统一转小写，防"Teacher / teacher"绕过计数。

**③ 状态表有容量上限（10000 键）+ LRU 淘汰。**
这条容易被忽略：攻击者若伪造十万个学号来撞库，限流器的字典会无限增长，
**限流器自己变成内存耗尽入口**。所以必须有上限，且满了就淘汰最久未用的键——
真实的爆破会集中在少数几个账号上，淘汰掉的都是被扫过一次的垃圾键。

### 11.3 运维怎么用

```bash
# 看当前有没有人正在被锁（locked 突然从 0 跳到几十 = 正在被撞库）
curl -s localhost:8000/api/security/stats -H "Authorization: Bearer <teacher_token>"
# {"limiter":{"tracked":0,"locked":0,"max_fails":5,"lock_seconds":300,...},
#  "trust_proxy":false,"slow_request_ms":1000}

# 查失败登录来源
curl -s "localhost:8000/api/audit?limit=50" -H "Authorization: Bearer <teacher_token>" \
  | grep login.failed
```

可调参数（环境变量，改完重启生效）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `LOGIN_MAX_FAILS` | 5 | 连续失败几次锁定 |
| `LOGIN_LOCK_SECONDS` | 300 | 锁定多久 |
| `LOGIN_FAIL_WINDOW` | 900 | 计数窗口，超时自动清零 |
| `SLOW_REQUEST_MS` | 1000 | 超过多久记为慢请求 |
| `LAB_TRUST_PROXY` | false | **前置 Nginx 时才设 true**。默认不信任 `X-Forwarded-For`，因为直连部署下该头可被任意伪造，信任它等于关掉限流 |

### 11.4 两个必须知道的后果

1. **CSP 放开了 `'unsafe-inline'`**。前端是原生 HTML + 内联 `<script>` + `onclick`，
   没有构建链就没有 nonce，不放开这两个页面直接白屏。它仍挡得住外域脚本加载与表单外发，
   但不是"完全防 XSS"。要更严就得给页面加 nonce 或引入构建，那是另一笔成本。
2. **`security_test.py` 用临时 `DATA_DIR`**，不读不写 `data/app.db`，本机没 Docker 也能跑。
   它可以随时重跑，不影响生产数据。

### 11.5 JWT 吊销（v1.0.3）

v1.0.2 补了抗爆破，但 token 本身仍是"签出去就收不回"：JWT 无状态，最长 12 小时内
泄漏了只能干等过期。v1.0.3 加了吊销，选型与实现：

**选型：SQLite 吊销表，不用内存黑名单。** 内存黑名单一重启就清零——这台机器
`Restart=always`，重启是常规运维，重启后已吊销的 token 全部复活，等于没做。
SQLite 持久化的代价是每个请求多一次本地读（WAL 下微秒级），30 人课堂无感。
短 token + refresh 方案最正规，但要动前端轮询逻辑，教学平台不值得。

**实现要点：**

- 每个 token 签发时带随机 `jti`（教师与学生同一机制）
- 校验统一收口在 `decode_token`：签名、过期、吊销三查合一，不存在"某个接口忘了查"的旁路
- 吊销写入 `revoked_tokens` 表时**顺带清理已过期条目**，表不会随时间无限增长，也不需要额外定时任务
- `POST /api/auth/logout` 教师/学生共用；登出后原 token 立即 401，重新登录不受影响
- 旧版无 `jti` 的存量 token 向后兼容：跳过吊销检查不报错，等它自然过期

**运维意义**：发现 token 泄漏（或学生借同学设备看完忘退出），一次 `logout` 请求即解决。
配合 11.1 的失败登录审计，token 类风险从"只能等"变成"可处置"。
