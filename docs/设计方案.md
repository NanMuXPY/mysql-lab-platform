# MySQL 实验环境一键交付平台 · 设计方案

> 定位：面向高校实验课的数据库环境交付平台。教师一次操作完成全班实验环境下发，学生用本地工具直连自己的独立 MySQL 实例。
> 本文档用途：开发实现依据与运维接手参考。

---

## 一、项目定位与岗位价值

**要解决的问题**：实验课教师目前要为学生逐个装 MySQL、建库建表、发账号，课前准备 1–2 小时，且版本不一致、学生误删库、课后环境不清算。

**平台做的一件事**：把"环境"当作可编排的资源，一键交付、限时占用、到期回收。

**对应通用云计算岗的能力项**：

| 岗位要求 | 本项目中的体现 |
|---|---|
| 云资源编排与自动化 | 容器生命周期 API 化，批量下发与回收 |
| 网络与安全 | 端口段规划、安全组策略、白名单、库级授权 |
| 资源配额与容量规划 | CPU/内存限额、并发上限、单机承载测算 |
| 运维与可观测性 | 审计日志、状态看板、异常自愈、告警 |
| 成本意识 | 单机容器方案替代多实例 RDS，按课表启停 |
| 交付能力（FDE 属性） | 教师端零命令行，全程 Web 操作，含连接信息一键导出 |

## 二、系统架构

```
教师浏览器 ──┐
             ├─→ Nginx（443，反向代理 + TCP 端口转发）
学生浏览器 ──┘        │
                      ├─→ 管理服务（FastAPI + Docker SDK）
                      │      ├─ 鉴权与角色（教师 / 助教 / 学生）
                      │      ├─ 实验单管理（开课 · 重置 · 回收）
                      │      ├─ 端口分配器（33001–33100 池）
                      │      └─ 审计日志写入
                      │
                      └─→ Docker Engine（单机）
                             ├─ 每学生 1 个 mysql:8.0 容器
                             │     · --cpus=0.5 --memory=256m
                             │     · 独立数据卷 /data/labs/<lab_id>/<student_id>
                             │     · 独立端口映射 0.0.0.0:33017→3306
                             └─ 初始化：挂载模板 SQL，容器首启自动导入
```

**为什么用容器而不是 RDS**：一个班 30 人，RDS 30 个实例成本不可接受（每月数千元）；容器方案在同一台 4C8G ECS 上即可承载，成本一份机器钱。教学场景是可信环境，容器共用内核可以接受——这一点必须主动说明，不能假装它是强隔离。

## 三、核心流程（教师视角 4 步，学生视角 1 步）

**教师开课**
1. 选实验模板（模板 = 建表 SQL + 初始数据 + 题目说明）
2. 填班级、人数、时长（如 120 分钟）、允许访问的网段
3. 点"下发" → 平台批量创建容器、初始化数据、生成每人账号
4. 导出连接信息表（学号 / 主机 / 端口 / 库名 / 账号 / 密码），或直接发给学生端页面

**学生上课**
打开学生端页面 → 看到自己的 IP、端口、账号密码 → 用 Navicat / DataGrip / `mysql` 命令行直连 → 做实验

**异常与收尾**
- 学生改坏数据 → 教师点"重置"：删容器 → 用同一数据卷重建 → 重跑初始化 SQL（10 秒内完成）
- 到点 → 平台自动停容器（保留数据卷，不删数据）
- 学期结束 → 批量删除容器与数据卷，释放磁盘

**容器状态机**：`待创建 → 创建中 → 运行中 → 已停止 → 已回收`，任何一步失败必须落到 `创建失败` 并回滚端口占用（避免端口泄漏，这是最容易出的 bug）。

## 四、数据模型（6 张表）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | id, 工号/学号, name, role, password_hash, created_at | 角色：teacher / assistant / student |
| `templates` | id, name, description, init_sql, version | 实验模板，SQL 存文本或对象存储路径 |
| `labs` | id, template_id, teacher_id, name, duration_min, allowed_cidr, status, starts_at, ends_at | 一次"开课"就是一条实验单 |
| `instances` | id, lab_id, student_id, container_id, volume_path, port, db_name, db_user, db_pass_enc, status, created_at | 核心表，一学生一条 |
| `port_pool` | port, instance_id, leased_at | 端口租约，防止端口复用冲突 |
| `audit_logs` | id, actor_id, action, target, detail, ip, created_at | 创建/重置/回收/登录全留痕 |

学生密码用对称加密存（如 AES，密钥走环境变量或 KMS），**不存明文**；教师端只在创建时展示一次，之后只能重置。

## 五、API 设计（MVP 只需 8 个接口）

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/auth/login` | 登录，发 JWT |
| GET | `/api/templates` | 模板列表 |
| POST | `/api/labs` | 创建实验单（含人数、时长），异步批量建容器 |
| GET | `/api/labs/{id}` | 实验单详情 + 每台实例状态 |
| POST | `/api/instances/{id}/reset` | 重置单台实例 |
| POST | `/api/labs/{id}/stop` | 整单停止（保留数据卷） |
| DELETE | `/api/labs/{id}` | 回收整单（删容器 + 删卷） |
| GET | `/api/labs/{id}/export` | 导出连接信息 CSV |

异步设计要点：30 个容器串行创建约 30–60 秒，创建接口立即返回任务 ID，前端轮询进度；后台用线程池限并发（如 5 个并行），避免瞬时压垮 Docker 与磁盘 IO。

## 六、网络与安全（学生直连的关键部分）

学生用本地工具直连，意味着 3306 类端口要暴露在公网，这是本项目最大的风险点，四条硬约束：

1. **端口段收敛**：只用 33001–33100，安全组只放通这一段，且限制源 IP 为校园网段（`allowed_cidr` 字段落地）；教师离职/课程结束立即收回。
2. **一人一账号，库级授权**：每个容器内建 `stu_<学号>` 账号，只对该学生的库授予 `ALL PRIVILEGES`，禁止跨库；`root` 密码只有平台知道，从不发给学生。
3. **强密码 + 防爆破**：16 位随机密码；MySQL 8 开启 `require_secure_transport`（自带自签证书即可满足教学场景），或至少限制 `max_connect_errors`。
4. **容器收敛**：`--cap-drop ALL`、非 root 用户运行、`--pids-limit=200`、只挂载自己的数据卷目录；不挂 Docker socket 给容器内部。

补充一条运维视角的判断：容器共用内核，**不是安全边界**。若将来面向不可信用户（如公网付费学员），要换成"每人一台轻量云主机"或 KVM 隔离，架构上把创建实例抽象成 provider 接口，换实现不改上层。

## 七、容量与成本测算

单容器内存基线：MySQL 8 默认配置约 200MB，调整 `innodb_buffer_pool_size=64M`、关闭 `performance_schema` 后可压到约 100–120MB。

| ECS 配置 | 可承载学生数 | 场景 |
|---|---|---|
| 2C4G | 10–12 人 | 单班小课 |
| 4C8G | 20–25 人 | 推荐起点，两班并行 |
| 8C16G | 40–50 人 | 全年级开课 |

成本策略：按课表启停（无课不占资源）；数据卷用本地盘而非云盘；一台机器承载全专业实验课，年均成本低于给学生发放云主机。

## 八、部署与可观测性

- **部署**：管理服务本身用 `docker-compose` 部署（nginx + api 两个容器），`restart: unless-stopped`；数据卷持久化元数据库。
- **日志**：应用日志 + 审计日志分离；容器日志限制 `--log-opt max-size=10m`，防止磁盘写满（教学平台最常见的线上事故）。
- **监控**：主机 CPU/内存/磁盘水位 + 容器数量 + 创建失败率三个指标；磁盘 >80% 告警（数据卷会持续增长）。
- **自愈**：容器异常退出由 `--restart=on-failure` 兜底；平台每日巡检"状态与 Docker 实际不一致"的实例并纠偏。

## 九、MVP 范围与迭代

**P0（先跑通，约 3 天）**
教师登录 → 建模板 → 创建实验单（人数/时长） → 批量建容器并初始化 → 导出连接 CSV → 单台重置 → 整单停止/回收。

**P1（好用，约 3 天）**
到期自动回收（定时任务）、审计日志页面、实例状态看板、学生端只读页面（查自己的连接信息）。

**P2（加分，视时间）**
自动评分（跑标准答案比对结果集）、题库与模板管理 UI、多机扩展（按 provider 抽象成 SSH + Docker 远程）、监控告警接入。

## 十、项目简介

> **MySQL 实验环境一键交付平台**｜独立设计与开发
> **项目背景**：实验课教师需为全班手工准备 MySQL 环境，课前耗 1–2 小时，版本不一、误删库频发、课后环境不清算。
> **职责**：独立完成架构设计、容器编排与生命周期管理、端口与权限隔离方案、批量下发与回收、审计与监控设计。
> **实测成果**：教师一次操作即可完成 30 人环境交付，课前准备从 2 小时降至 1 分钟内；实现一人一实例的端口、账号、数据卷三重隔离，全操作留审计日志；按课表启停与到期自动回收，单台 4C8G 云服务器承载两班并行实验（20–25 实例），资源成本较逐一发放云主机大幅下降。

**一句话概括**：把"配环境"从手工劳动变成一个 API——老师点一下，全班环境就绪，用完自动回收。

## 十一、常见疑问与说明

1. **为什么用容器不用 RDS？** → 教学场景是可信用户，容器单机可承载 20+ 实例，成本是 RDS 的几十分之一；并用 provider 抽象预留了换 KVM/云主机的路径。
2. **容器隔离够吗？** → 不够，容器共用内核。所以做了三层收敛：库级授权、cap-drop、非 root；对外只暴露端口段并限源 IP。不可信用户场景我会换实现。
3. **30 个容器同时创建会不会卡死？** → 后台任务 + 并发上限 5，创建接口立即返回任务 ID 轮询；失败回滚端口租约。
4. **学生把机器跑满怎么办？** → `--cpus=0.5 --memory=256m --pids-limit`，单实例无法拖垮主机；平台限制单实验单实例总数。
5. **磁盘会不会写满？** → 容器日志限 10MB 轮转，数据卷按学期清理，磁盘水位 80% 告警。
6. **怎么保证学生进不了别人的库？** → 一人一容器一账号，账号只对自己库有权限；不同容器天然不同实例，即使拿到别人端口也没有凭证。
7. **重置为什么快？** → 删容器保留数据卷目录，重建后重跑初始化 SQL；不重建整台机器，也不做数据回滚。
8. **这套东西的可运维性体现在哪？** → 审计日志、状态看板、每日一致性巡检、失败率与水位告警——出问题能定位到具体实例。
