# 性能重审报告：MySQL 实验环境一键交付平台

> 2026-10-31，基于当日 20 实例真实压测数据（`docs/压测报告-20261031-0133.md`）。
> 结论先行：**当前 2核4G 机器的容量天花板约 25 个实例，4核8G 约 55 个**；
> 交付速度瓶颈不在代码在 CPU（MySQL 首次初始化），代码层面无 P0 级性能缺陷。
>
> **【当日更新】金镜像预初始化已落地并实测**（见文末"金镜像优化实录"）：
> 20 实例交付 141.5s → **60.6s（2.3 倍）**，单实例就绪 85.6s → 39.0s（首个 14.7s）。

## 一、实测基线（写进项目简介的数字）

| 指标 | 数值 | 说明 |
|---|---|---|
| 20 实例交付总耗时 | **141.5s** | 并发 5，走平台真实 API 全链路 |
| 单实例平均就绪 | **85.6s** | 首个 34.2s / 尾个 141.5s |
| 单容器实际内存 | **115 MiB** | 限额 256MiB，0.5 核 |
| 20 容器内存合计 | **2295 MiB** | 主机剩 547MB available，无 OOM |
| 真实登录成功率 | **20/20** | 容器内 SELECT 1 完整握手 |

**容量公式**：`max_instances ≈ (总内存 MB − 700 系统开销) ÷ 130`
- 2核4G（本机 3563MB）→ **约 22 个**
- 4核8G → **约 55 个**（端口池 100 上限前内存先到）
- 结论：交接文档"4C8G 扛 20 实例"的承诺有 2.7 倍余量，甚至 2核4G 就能扛 20。

## 二、做对了的（设计层无需改动）

1. **容器硬限额**（256MB mem + memswap 同值 + pids 200）：单容器内存被钉死在 115MB，
   容量可精确预测——这是敢承诺"扛全班"的根本。
2. **SQLite WAL + BEGIN IMMEDIATE + 进程内写锁**：本平台写 QPS 极低
   （一次部署 20 人 ≈ 60 次写，摊到 140 秒），单文件库完全够，且省掉一个 MySQL 依赖。
3. **端口部分唯一索引**：并发租端口冲突由数据库层兜底，应用层只重试——压测 20 并发零端口冲突。
4. **general_log 增量采集（字节偏移）**：不做全量解析，错题诊断按钮的采集成本
   只与"新增日志量"相关，与历史无关。
5. **前端懒加载**：学生总览/审计日志按需加载不进轮询；实验单 DOM 未变化不重建。

## 三、瓶颈清单（按优先级）

### P1-1 MySQL 首次初始化占创建耗时的大头
- 现象：首个实例 34.2s、5 并发一批 ~35s——全是 `mysqld --initialize` + 模板导入。
- 优化（二期）：**预初始化金镜像**——把初始化好的 datadir 做成模板镜像，
  创建时只需拷贝目录启动，单实例 ~7s → ~2s，20 人交付有望进 30s。
- 或加大并发：4核8G 上 `LAB_CREATE_CONCURRENCY=10`（现默认 5），总耗时约减半，改环境变量即可。

### P1-2 主机无 swap，OOM 即事故
- 现状：available 547MB 时还能扛，但学生写大查询（如全表 ORDER BY）会涨内存，
  触发 OOM killer 可能杀到 uvicorn 本体。
- 建议：服务器加 2GB swapfile 兜底（容器 memswap 已锁死不影响隔离语义）；
  uvicorn 建议用 systemd 托管自动拉起（任务 8 一并做）。

### P1-3 错题诊断是同步 CPU 操作
- `sqlglot` 解析 20 实例新增日志在请求线程内完成（FastAPI 同步路由跑线程池，
  不阻塞事件循环，但吃 GIL）。20 实例 × 几百条新增 SQL 时诊断按钮要等几秒。
- 优化：采集结果落库后按 lab 缓存 30s TTL；日志量超阈值（如单实例 >5000 条新增）
  时截断并提示。当前教学规模（≤50 人）可接受，列入二期。

### P2-1 SQLite 单写者
- 全局写锁意味着审计日志、偏移表、实例登记串行。当前写频率（<1 QPS）无感；
  若二期上"自动评分"高频写，需要改批量写或换 MySQL 元数据库。

### P2-2 uvicorn 单进程
- 刻意单 worker（SQLite 跨进程写锁会复杂化）。2 核下轮询+采集并存时偶发延迟，
  可接受；不要盲目加 worker，先解决 P1-3。

### P2-3 前端轮询放大
- 每个打开的浏览器每 5s 发 1+N 个请求。50 个实验单 × 多教师同时开页面，
  约 60 req/5s——FastAPI 无压力，但列表全量对比 HTML 字符串的收敛逻辑
  在 100+ 实验单时会变慢，届时改增量接口。

### P3 磁盘
- 每实例数据卷 ~180MB（含系统表），40GB 盘可容 ~180 个实例生命周期；
  回收即删卷，磁盘不是瓶颈。镜像 mysql:8.0 服务器已缓存，创建无拉取开销。

## 五、金镜像优化实录（2026-10-31 凌晨）

**方案**：`scripts/make_gold.py` 一次性完整初始化 mysql:8.0，把系统表 datadir
（196 MiB / 149 文件）固化为宿主机模板。建实例时 `cp -a` 拷贝模板
（实测 0.2s），entrypoint 检测到 datadir 非空跳过 `mysqld --initialize`
（原创建耗时的大头），随后一次 `docker exec` bootstrap SQL 完成建库/
建号/授权/换 root 密码/灌模板。金镜像缺失或引导失败**自动回退慢路径**。

**实测对比**（同为 2核4G、并发 5、20 实例、模板相同）：

| 指标 | 慢路径 | 金镜像 | 提升 |
|---|---|---|---|
| 交付总耗时 | 141.5s | **60.6s** | 2.3× |
| 单实例平均就绪 | 85.6s | **39.0s** | 2.2× |
| 首个实例就绪 | 34.2s | **14.7s** | 2.3× |
| 成功率 / 真实登录 | 20/20 | 20/20 | 持平 |

**踩坑记录（说明可用）**：第一版 bootstrap 立即失败率 100%——
`wait_until_running` 的 TCP 探测连的是 docker-proxy，容器一起它就监听，
mysqld 未就绪时 TCP 也"通"，bootstrap 撞上 ERROR 2003 全部回退慢路径
（比纯慢路径还慢 35s，因为白拷了 196MB）。修复：bootstrap 自带
连接类错误重试（30 次 × 2s），SQL 语法错误不重试。修复后回退 0 次。

**重置同步受益**：教师"重置学生实例"走同一条快路径，重置时间同步下降。

**结论**：2核4G 上 20 人实验单已进入 1 分钟内交付。8G 实测 50+ 实例
只在需要项目简介数字时才值得开——不用换机器，临时开一台按量 4C8G 跑一轮
压测即可（约 ¥1）。
